# 默认看板临时 Agent 耗时优化与验收

本次修改保留模型、思考配置、超时、输出上限、三期 MT/ST 分析范围和看板六列。性能目标是成功样本中位耗时降低至少 20%，质量单独验收，不能用结构校验成功代替事实核查。

## 改动边界

| 改动 | 主要文件 | 保留的约束 |
| --- | --- | --- |
| 草稿与增量复核 | `analysis/drafts.ts`、`analysis/report.ts`、`analysis/agent.ts` | 完整报告校验、原始证据和最终 `report.json` 格式 |
| 确定性损失展示 | `tool/loss-output.ts`、`tool/loss-tools.ts`、`analysis/evidence.ts` | 完整冻结快照、原始行索引、自主 SQL/Python 调查 |
| 耗时观测与对照 | `analysis/metrics.ts`、`default/run.ts`、`scripts/benchmark-daily-analysis.ts` | 模型和业务计算参数、超时降级行为 |

三部分采用独立模块；回退时分别恢复对应模块及 Agent 中的接入点。观测和评估可独立保留。已有 `report.json` 的消费者无需迁移。

## 提交协议

1. `submit_analysis` 校验并保存完整草稿，返回新 `draft_id`。重复提交使旧 ID 失效。
2. 后续模型轮次复查证据，必要时调用 `get_analysis_draft` 或补查，再调用 `finalize_analysis`。`verification` 必填，`updates=[]` 表示没有修改。
3. 服务端在副本上应用修改并完整校验，失败保留原草稿。有效复核返回实际修改及合并后的报告，生成新的草稿 ID。
4. 模型在后续轮次核对修改是否落入正文。补交修改会再次生成待确认草稿；用空修改确认后才调用发布回调。

第三步的合并确认来自真实评估发现：模型可能在复核说明中列出多项修正，但只提交部分 `updates`。返回实际合并报告能检查这个遗漏，又不要求模型重新生成整份报告。它仍然不能保证模型发现所有正文事实错误。

修改示例：

```json
{
  "draft_id": "服务端返回的当前ID",
  "verification": "逐条核对了日期、损失行与日均分母，修正比较说明。",
  "updates": [
    { "op": "update_period", "period": "month", "comparison": "本月覆盖14个有数据业务日；按相同分母比较。" },
    { "op": "update_item", "period": "week", "kind": "MT", "priority": 1,
      "changes": { "measure": "核对等待原因，并于下周比较同口径日均损失。" } }
  ]
}
```

新增、删除和重排条目使用 `replace_group`，其 `group` 包含 `no_findings_reason`、`evidence_ids`、`items`。同一请求不得重复修改同一目标，或同时替换分组和修改该组条目。字段及 JSON 解析错误返回路径与可获取的位置，不自动修补损坏 JSON。

## 摘要完整性

`measure_loss` 的 `view` 在不超过 32 行、12 KiB 展示预算时包含全部原始行；否则按 MT/ST 提供状态合计、占比和各自前十条机台—状态记录。排名使用未舍入小时，并按机台和状态打破并列。原始 `row_index` 在排序前固定，派生统计没有可冒充实测行的索引。

`scope` 和 `range` 标注筛选条件与日期。覆盖日数取类型级一致分母，不累加各机台天数；空结果不证明零损失，异常或零分母不产生占比。展示预算不足时缩短排名和状态清单，完整性标记及总行数保留。原始证据被截断时不生成全量统计。`execute_sql` 保持原有预览方式。

## 耗时与质量评估

脚本只运行分析，使用 SQLite backup 一致副本，不调用同步接口、不发布默认看板。三组顺序为旧/新、新/旧、旧/新，全部串行。通过 `--candidate-root` 指定冻结的新版本目录，`--snapshot` 可复用一致备份。

每次保留报告、完整证据和事件；`metrics.json` 包含模型客户端观测区间、工具时间、输出量、阶段及未完成区间。客户端时间包含网络等待、生成及可能的重试，不代表服务端推理时间。超时样本单列；旧版成功少于两次时不认定性能目标。

质量核查包括报告结构、损失引用逐行复核、正文关键数值和日期、机台及措施依据，以及旧版至少两次出现且证据成立的重要问题是否保留。报告文字和建议顺序无需一致。

成功旧版的模型客户端观测时间中位数为 247.9 秒，约占总耗时 88%；SQL 与损失查询仅约 2.6 秒。草稿与复核生成区间合计中位数为 177.3 秒。新版模型观测中位数降至 186.4 秒，工具中位数由 15.4 秒降至 2.7 秒；主要收益来自模型生成/调查减少及机械 Python 调用减少，SQL 仍不是主要瓶颈。不同阶段中位数不能相加当作某一次运行的时间分解。

结构回归全部通过：`npm run check`、`npm test`（251 项通过），包括草稿不可变合并、重复/过期目标、补交修改后确认、压缩后读取草稿、纯文字回复修复、补查证据、摘要预算与原始行号、超时终止及降级。三份新版均通过完整报告结构与损失引用合法性校验，并保留两份成功旧版中重复出现的 10 类高优先级问题；这不等于全部正文事实正确。

事实核查发现以下未解决问题，不能认定“分析质量无明显退化”已经得到验证：

- 新版 1 在月度比较中抄入周度 ST 可用率，并将最大状态损失称为第二大；部分机台事实缺少条目级实际来源引用。
- 新版 2 把季度保养机台 ADH125 写入月度结论。独立标准查询确认本月 PM 为 ADH186 126.4803 小时、ADH150 1.1569 小时，没有 ADH125 本月 PM 匹配记录；另有缺少依据的“超出常规保养时长”判断。
- 新版 3 的 ADH196 单机问题引用了 ST 全类型 HangUp 损失行，使展示小时成为周 185.1／月 533.6，而该机实测为周 124.7／月 214.5。还存在把非单调历史写成“逐月加重”、复核声称补充引用却未修改 `evidence_ids` 的情况。
- 旧版也存在部分排名、历史趋势及跨期数字错误。此次没有把旧版文本当作真值，均按冻结证据复核；这些既有缺陷不构成新版通过质量门槛的理由。

合并与摘要计算未发现污染草稿或算错原始损失数据；主要缺口是正文事实与具体证据、机台范围之间缺少程序可核对的对应关系。下一步应优先约束关键事实与来源、单机问题与单机损失行的一致性，并改善证据 ID 字段的错误修复反馈，再按相同门槛复测。增加模型确认不能替代这层事实核对。
